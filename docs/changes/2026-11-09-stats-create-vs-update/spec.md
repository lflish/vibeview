# 统计页区分新建和更新

状态：草案　阶段：dev-requirements　待关口：评审　等级：L1　规模：标准　创建：2026-11-09　更新：2026-11-09

## 背景与目标

为什么要做：资源支持版本以后（v1.4.0），同一个链接可以反复更新（`dview upload` 同一路径、`--id`、模板渲染），但管理统计只在资源第一次创建时记一条上传事件，**更新完全不计**。需求稿、原型这类页面主要靠更新迭代，统计页因此低估了实际活动，也看不出哪些页面在持续迭代。resource-versions spec 当时把这件事推迟到“以后需要时再做”。

现状数据（生产，2026-11-09 只读统计）：48 个资源里 3 个更新过，保留着 5 个更新版本，这 5 次更新都没有进统计。

做完的样子：统计页能分别看到新建和更新的次数和体积；每次更新都留下一条记录，删除资源或删除历史版本后记录不减少。

## 前提

- P1 更新现在完全不进统计（`lib/statistics-store.js` 的上传事件按资源 id 只记一次；`server.js` 的 `updateResource` 不调用统计）。
- P2 只把“上传了一个新版本”算作更新；改访问码、改分类、改简介、删除历史版本都不算。
- P3 已经发生的更新可以从资源元数据里保留的版本记录回填（每个版本有时间和大小）；被保留上限删掉的旧版本、已删除资源的更新无法还原，统计页照现有方式标明“历史可能不完整”。

## 假设

| # | 假设 | 依据 |
|---|------|------|
| H1 | 一次更新的体积 = 这一个新版本的大小，不是资源所有版本的总大小 | 和新建一样，按“这次上传了多少”计 |
| H2 | 删除资源或删除历史版本，不减少已经记下的更新次数和体积 | 现有口径：删除不减少历史上传 |
| H3 | 来源、项目、类型筛选对更新同样生效；来源取更新时的账户，项目按资源当前项目归类（和现有上传一致） | 现有统计口径 |
| H4 | 统计日志里的更新事件和上传事件一样只保存最小字段（资源 id、版本号、类型、字节数、来源、时间），不保存文件名、简介、访问码、token | 现有隐私约定（invariants） |
| H5 | “当前文件数/体积”不变：更新不增加文件数，存量体积照旧是资源所有保留版本之和 | 现有口径，resource-versions spec |
