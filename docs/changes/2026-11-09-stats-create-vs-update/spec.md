# 统计页区分新建和更新

状态：测试中　阶段：dev-test　待关口：C　等级：L1　规模：标准　创建：2026-11-09　更新：2026-11-09

## 背景与目标

为什么要做：资源支持版本以后（v1.4.0），同一个链接可以反复更新（`dview upload` 同一路径、`--id`、模板渲染），但管理统计只在资源第一次创建时记一条上传事件，**更新完全不计**。需求稿、原型这类页面主要靠更新迭代，统计页因此低估了实际活动，也看不出哪些页面在持续迭代。resource-versions spec 当时把这件事推迟到“以后需要时再做”。

现状数据（生产，2026-11-09 只读统计）：48 个资源里 3 个更新过，保留着 5 个更新版本，这 5 次更新都没有进统计。

做完的样子：统计页能分别看到新建和更新的次数和体积；每次更新都留下一条记录，删除资源或删除历史版本后记录不减少。

## 完成条件

R1–R5 的场景都有自动化测试（统计单元测试、集成测试、`--browser` 浏览器测试）并全部通过，`SMOKE_SKIP_RENDER=1 npm test` 和 `npm run test:browser` 通过；上生产后，管理统计页里能看到回填的历史更新（上线前生产有 5 个保留的更新版本）。

## 前提

- P1 更新现在完全不进统计（`lib/statistics-store.js` 的上传事件按资源 id 只记一次；`server.js` 的 `updateResource` 不调用统计）。
- P2 只把“上传了一个新版本”算作更新；改访问码、改分类、改简介、删除历史版本都不算。
- P3 已经发生的更新可以从资源元数据里保留的版本记录回填（每个版本有时间和大小）；被保留上限删掉的旧版本、已删除资源的更新无法还原，统计页照现有方式标明“历史可能不完整”。

## 做法与范围

做法：B —— 记录每次更新；数字卡片、趋势图、月历、当日明细、最近活动、排行都区分新建和更新。放弃 A（只在卡片和活动里区分）：趋势图是这页的主体，只分卡片看不出哪几天在集中迭代。
范围模式：选择性扩展

要做：
- 每上传一个新版本，记一条“更新”事件（普通上传 `--id`、`.dview.json` 自动更新、模板渲染都算）
- 回填已有资源里保留的历史版本（E1）
- “上传”= 新建 + 更新；页面上各处同时给出“新建 X · 更新 Y”
- 趋势图、月历、当日明细、最近活动、类型分布、项目和来源排行区分新建和更新（E2）
- 统计口径弹窗补充“更新”的定义

不做：
- 访问统计按版本区分（打开的是哪个版本）：和本需求无关，工作量大
- 管理端资源列表里的版本显示：已有，不动
- 改访问码、分类、简介，删除历史版本：都不算更新（P2）

推迟到以后：
- E3 “迭代最多的页面”排行（按更新次数）

已有可复用：
- `lib/statistics-store.js` 的预写意图（先写 pending，提交后移入正式日志）和启动回填：更新事件沿用同一套做法
- `versions.list(meta)`：每个版本的序号、时间、大小，用来回填
- 统计页现有的筛选、月历联动、当日分页弹窗

理想状态对照：现状 只看得到“新建了多少页面” → 本次 看得到新建和迭代各多少、哪天在迭代 → 一年后 能看出哪些页面被反复评审、迭代到定稿（配合 review-comments）

## 需求与验收场景

### R1 记录更新

系统必须在资源每成功上传一个新版本时，记一条更新事件；其他操作不记。

- **R1.1 用 `--id` 更新 HTML 页面**
  假如 账户 alice 已有一个 HTML 资源（v1）
  当 alice 上传同一 id 的新文件，生成 v2
  那么 今日上传 +1，其中更新 +1、新建不变；这条更新的体积等于 v2 的文件大小
- **R1.2 更新多页面站点**
  假如 一个站点资源
  当 上传新的站点目录生成新版本
  那么 记一条类型为“站点”的更新，体积等于新版本解压后的大小
- **R1.3 模板渲染生成新版本**
  假如 一个由模板渲染出的资源
  当 用 `dview render <模板> --data … --id <id>` 再渲染一次
  那么 记一条更新
- **R1.4 失败的更新不计**
  假如 更新请求被拒（类型不一致 400、更新别人的资源 403、超出配额 429）
  当 查看统计
  那么 新建和更新次数都不变
- **R1.5 不是新版本的操作不计**
  假如 一个有 3 个版本的资源
  当 修改访问码、修改分类或简介、删除第 2 版
  那么 更新次数不变，之前记下的更新也不减少
- **R1.6 删除资源后历史保留**
  假如 一个资源被新建后更新过 2 次
  当 删除这个资源
  那么 上传次数仍包含这 1 次新建和 2 次更新；当日明细里这几行的文件名隐藏，显示“已删除”
- **R1.7 更新途中服务退出**
  假如 新版本已经写进资源元数据，但更新事件还没进正式日志时，服务进程退出
  当 服务重启
  那么 这次更新被记一次；如果新版本没写进元数据，就不记

### R2 回填已有的更新（E1）

系统必须在新版本第一次启动时，把现存资源里保留的历史版本记为更新，并标为“回填”。

- **R2.1 回填保留的版本**
  假如 一个资源保留着 v1、v2、v4（v3 已删除）
  当 新版本第一次启动
  那么 记 2 条回填的更新（v2、v4），时间和体积取各自版本的记录
- **R2.2 重启不重复**
  假如 已经回填过
  当 服务重启、或删除 SQLite 索引后重启
  那么 更新次数不变
- **R2.3 版本记录无效时跳过**
  假如 某个版本缺少创建时间或时间无效
  当 回填
  那么 这个版本不记，计入统计口径里的“跳过”数量，不编造时间
- **R2.4 回填前已删除的资源**
  假如 某资源在新版本上线前已经删除
  当 回填
  那么 它的更新补不回来；统计页照现有方式提示“历史可能不完整”

### R3 统计页区分新建和更新

系统必须在统计页的各个部分同时给出新建和更新。

- **R3.1 数字卡片**
  假如 今天新建 2 个、更新 3 次
  当 打开统计页
  那么 “今日上传”显示 5 个，下方写“新建 2 · 更新 3”；“近 30 天上传”同样给出合计和拆分
- **R3.2 趋势图**
  假如 所选范围内有新建也有更新
  当 查看每日趋势
  那么 每天的柱子分成新建和更新两段，有图例；鼠标悬停或键盘聚焦时显示“新建 X · 更新 Y”；切换到“上传体积”时同样分两段
- **R3.3 月历和当日明细**
  假如 某天有 1 次新建、2 次更新
  当 点击这一天
  那么 月历格子显示合计 3；当日明细列出 3 行，更新行标“更新 · v<n>”，新建行标“新建”；弹窗分页照常
- **R3.4 最近活动**
  假如 最近有新建、更新和删除
  当 查看最近活动
  那么 分别显示“新建”“更新 v<n>”“删除”；回填的事件不作为新活动显示
- **R3.5 类型分布和排行（E2）**
  假如 范围内各类型、各项目、各来源都有新建和更新
  当 查看类型分布、按项目、上传来源
  那么 各项给出合计，并能看到其中新建和更新各多少
- **R3.6 筛选**
  假如 选了某个来源、项目或类型
  当 查看统计
  那么 新建和更新都按筛选计算；资源当前所属项目变了时，它的更新跟着按当前项目归类（和现有新建的口径一致）
- **R3.7 没有更新时**
  假如 所选范围内一次更新都没有
  当 打开统计页
  那么 各处显示“更新 0”，页面布局正常，没有报错
- **R3.8 统计口径说明**
  假如 管理员不清楚“更新”指什么
  当 打开“统计口径”弹窗
  那么 能看到：更新指上传了新版本；改访问码、分类、简介，删除历史版本不算；历史更新从保留的版本回填，已清理的版本无法还原

### R4 接口兼容

系统必须保持现有统计接口的字段和含义可用，只新增字段。

- **R4.1 原字段仍可用**
  假如 有脚本读取 `/admin/api/statistics` 的 `summary.uploads.count`
  当 升级后再读
  那么 字段还在，值为新建 + 更新的合计（Q1 选 A）；另有字段分别给出新建和更新
- **R4.2 权限不变**
  假如 未登录，或只带上传 token
  当 请求统计接口
  那么 仍返回 401

### R5 隐私

系统必须让更新事件和现有上传事件一样，只保存最小字段。

- **R5.1 日志和接口不含敏感信息**
  假如 更新过的资源文件名、简介里含有标记字符串，账户 token 也是标记字符串
  当 读取统计日志目录里的所有文件，以及统计接口的返回
  那么 日志里找不到文件名、简介、token，也没有访问码和访问哈希；接口返回里找不到简介、token、访问码和访问哈希；仍保留的资源照旧返回文件名，已删除的资源文件名为空

## 非功能要求

- 性能：统计请求不因更新事件而扫描资源文件或版本目录；和现在一样启动时加载一次。

## 假设

| # | 假设 | 依据 |
|---|------|------|
| H1 | 一次更新的体积 = 这一个新版本的大小，不是资源所有版本的总大小 | 和新建一样，按“这次上传了多少”计 |
| H2 | 删除资源或删除历史版本，不减少已经记下的更新次数和体积 | 现有口径：删除不减少历史上传 |
| H3 | 来源、项目、类型筛选对更新同样生效；来源取更新时的账户，项目按资源当前项目归类（和现有上传一致） | 现有统计口径 |
| H4 | 统计日志里的更新事件和上传事件一样只保存最小字段（资源 id、版本号、类型、字节数、来源、时间），不保存文件名、简介、访问码、token | 现有隐私约定（invariants） |
| H5 | “当前文件数/体积”不变：更新不增加文件数，存量体积照旧是资源所有保留版本之和 | 现有口径，resource-versions spec |
| H6 | 一个资源的同一个版本号只记一次更新；之后不会有别的版本复用这个序号 | 新版本序号 = 现有最大序号 + 1，当前版本（最大的）不能删 |
| H7 | 统计页“上传体积”合计 = 新建体积 + 更新体积；“当前存量”照旧 | Q1 选 A |
| H8 | 新建的体积只算第 1 版；回填新建事件时用 v1 的大小，不用资源所有版本的合计；已经写进日志的事件不改写（日志只追加） | 否则同一份字节会在新建和更新里各算一次 |
| H9 | 更新事件的时间取这个版本记录里的创建时间（和资源元数据里显示的一致），实时更新和回填口径相同 | 跨午夜时当日明细、月历和版本历史对得上 |
| H10 | 没有新建记录的老资源（创建时间缺失或无效）被更新时，照样记更新；它的新建仍算缺失 | R1 “每个新版本都记一条”，不依赖新建记录 |
