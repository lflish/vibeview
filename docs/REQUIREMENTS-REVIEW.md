# vibeview 需求评估（高级评审）

> 日期：2026-10-08（Asia/Shanghai）  
> 范围：`docs/SPEC.md`、`docs/design-render-sidecar.md`、README、工作区未提交实现 vs 开放项（P0-10、P1-2..6、P2）  
> 性质：**产品/工程需求评审**（非实现清单重述）。观点明确，可直接拍板。

## 1. 执行摘要

- **产品定位清晰**：自托管「机器上传 → 不可猜测预览链接」工具，目标用户（运维 / Agent·CI / 单管理员）与非目标（SaaS、多管理员 RBAC、每请求浏览器沙箱）写得够硬，值得保持。
- **本轮三线（账户管资源、管理端 UX、生态 CLI）与核心价值同向**，本地实现面已经「能讲故事」：token=账户、配额、自助 API、管理端账户页、`dview`、integrations。
- **渲染 sidecar（P1-1）架构判断正确且克制**：主服务宿主机 + 单预览容器 + data `:ro`，明确不声称防访客 XSS——这是诚实的安全叙事，开源可信度高于「Docker = 安全」。
- **最弱环节不是功能，是验证与交付门禁**：P0-10 全链路冒烟未做；`smoke:render` 只盖语法/本地 render/502；本机无 Docker 实机；一大坨未提交 diff 尚未按可审 PR 切开。
- **SPEC §8 实现顺序已过时**：sidecar 已先于冒烟落地，文档仍写「先测再 sidecar」——跟踪状态与真实 backlog 脱节，会误导下一位贡献者。
- **最大产品/安全张力仍在**：公开 `/v` + 同源可能挂 `/admin` + HTML 直出执行。sidecar 解决「密钥不在预览进程」；**不**解决「恶意预览页打管理会话」。若 README/SPEC 只强调前者，运维会高估隔离。
- **P1 后半段（沙箱模式、UI 建账户、热加载、服务端分页）互不阻塞核心闭环**，但 P1-5/P1-6 会动「密钥存在哪、谁能写」——若不先定持久化模型，容易返工。
- **建议**：先冻结 SPEC 状态与 2～3 个开放问题答案 → **补 P0-10** → **拆 PR 合入**；沙箱/建账户/分域名一律排到合入之后按需开。

## 2. 产品一致性（开源自托管工具是否「站得住」）

### 2.1 一句话价值主张

> 给 AI/CI 一条命令，把 HTML/图/视频丢到你自己的小服务上，换回可分享的预览链接；管理员能管用量与滥用。

这条主张与当前实现、README、生态文档一致。**不要**在同一版本里再宣称「安全托管不可信 HTML」——与 P1-1 设计文书写的非目标冲突，也会稀释定位。

### 2.2 功能束是否互相支撑

| 能力束 | 是否服务主张 | 评价 |
| --- | --- | --- |
| 上传 + `/v/<id>` | 核心 | 稳 |
| token=账户 + 配额 + `/api/me` | 多机器不互相踩、可停滥用 | 稳；「账户」名略重，实际是 **named token**，文档已说明可接受 |
| 管理端 UX | 运维日常 | 稳；客户端分页在资源少时够用 |
| CLI / AGENTS / Action | 降低 Agent/CI 接入摩擦 | 稳；与「机器是一等公民」一致 |
| 渲染 sidecar | 生产加固预览面 | **可选增强**，不是 MVP；默认 `proxy_to_render: false` 正确 |
| sandbox / 截图 / 签名 URL | 改变威胁模型或分享模型 | 与「链接即分享 + 可信上传」部分正交，宜标可选 |

### 2.3 命名与心智

- 仓库 **vibeview**、npm/bin **dview**、Skill **dview-upload**：开源常见，但 SPEC/README 应固定一句「产品名 vibeview，CLI 名 dview」，避免贡献者以为要发两个包。
- 「账户」在 UI/API 出现，底层仍是 `config.yaml` 的 `tokens[]`：**可接受**，但 P1-5 若做成「真正的账户库」却仍叫同一套词，需在 SPEC 写清迁移，否则文档会漂。

### 2.4 结论

作为 **小团队/个人自托管 + Agent 友好** 的开源工具，范围是连贯的。风险在于把 P1/P2「安全增强」误读成必须项，或把 sidecar 卖成 XSS 方案——**产品叙事一旦膨胀，一致性就会碎**。

| 项 | 理由 |

| **P1-2 / P1-3** `direct \| sandbox` + CSP 分支 | 有价值，但是**第二安全故事**；默认仍应 `direct`（兼容内联脚本的 AI 产物）。先合入再做最小开关。 |

### 3.4 当前「已实现未提交」是否过载？

**略偏多，但仍是同一主题的合理一批**：账户 + UX + 生态 + sidecar。问题不在功能相干性，而在 **PR 粒度**（见 §5、§8）。功能上不必再砍本地代码；交付上必须切开或至少分 commit 说明。

| # | 风险 | 影响 | 可能性 | 缓解 |

| **R3** | **同源 `/admin` + 公开恶意 HTML**（设计 T1 + §7.3） | 管理 cookie 同站风险（视 CSRF/SameSite）；比「容器逃逸」更现实 | 中 | 短：Cookie `SameSite=lax` 已有，保持；文档建议生产 admin 别与预览同闲置会话。中：P2-1 分域。勿用「再加一层 Docker」假装解决 |

| **R5** | **超大未拆 PR + 密钥/账户持久化未定就做 P1-5** | Review 失败、回滚难；或把 token 写进错误位置 | 中 | 见 §5 拆 PR；P1-5 开工前书面定：`data/accounts.json` vs 写回 yaml vs 仅轮换展示——**三选一写进 SPEC** |

## 5. 优先级重排（相对当前未提交工作之后）

> 替换 SPEC §8「先 sidecar 再测」的过时序。下列为 **推荐真实顺序**。

| 序 | 动作 | SPEC | 产出 |
| --- | --- | --- | --- |
| **A** | 冻结开放问题最小集（见 §6）：预览默认 direct；P1-5 本阶段做/不做；PR 拆法；npm 不发布 | §9 | SPEC 状态改为「已定稿（本轮）」 |
| **B** | **P0-10** 全链路冒烟（临时 config + 独立 data） | P0-10、§7.1 | `scripts/smoke.sh` + `npm test`；补齐账户/配额/隔离/停用 |
| **C** | 整理提交并开 PR（建议拆，见下） | 工程收尾 | 可审、可回滚 |
| **D** | 有 Docker 的环境跑设计 §14 R2–R5（502 不回退） | P1-1 验收 | 勾掉「实机未验证」 |
| **E** | （可选）P1-2 最小 `preview.mode: sandbox` | P1-2/3 | 默认仍 direct |
| **F** | 仅当用户确认持久化模型后 → P1-5/P1-6 | P1-5/6 | 否则保持「改 yaml + 重启 / 运行时 disable」 |
| **G** | 体量上来再 P1-4；审计 P2-5；分域 P2-1 | — | 按痛点 |

### 建议 PR 拆分（意见）

1. **PR-A「账户 + 管理端 UX + README 账户段」**（P0-6/7/9 主体）— 产品主故事。  
2. **PR-B「生态：CLI / install / AGENTS / integrations / Action」**（P0-8）— 可独立审。  
3. **PR-C「渲染 sidecar」**（P1-1、P2-8、design 文档）— 设计已单独成文，适合独立 PR（与 design Q10 一致）。  
4. **PR-D「smoke」**（P0-10）— 可先于或紧跟 A，避免 A 合入无网。

若维护者带宽极低：**允许单 PR 多 commit**（commit 边界同上），但不要无说明的巨型单 commit。

## 6. 缺口 / 歧义（不答就会返工）

下列对应 SPEC §9，按「必须先答 / 可默认」分类。

### 6.1 必须先答（挡住正确排期）

1. **P1-5 本阶段要不要做？**  
   - 若 **不做**：管理端继续「yaml 配 token + UI 只能 disable」——写进非目标，关掉期待。  
   - 若 **要做**：必须先定 token 持久化：  
     - (a) 写回 `config.yaml`（糟：密钥文件被程序改、备份/权限噩梦）；  
     - (b) `data/accounts.json` + 启动合并（较干净，需热加载 P1-6）；  
     - (c) 仅「轮换」：生成新 token 展示一次，仍手改 yaml（半吊子）。  
   - **评审倾向**：本阶段 **不做 P1-5**；运行时 disable 已够控滥用。

2. **提交/PR 策略**：单 PR 还是拆？影响 review 与回滚。**倾向拆 3 个功能 PR + 1 个 smoke**（§5）。

3. **预览默认策略**：继续 `direct` 还是默认 sandbox？  
   - **倾向保持 direct**（AI 产物常依赖内联脚本）；sandbox 仅 opt-in（P1-2）。

### 6.2 可用文档默认值锁死（不必再问用户，但要写进 SPEC）

| 问题 | 推荐默认 |
| --- | --- |
| 预览是否永远公开 | **是**（nanoid）；签名 URL 进 P2 且默认关 |
| 多管理员 / 审计 | 多管理员本阶段不做；审计 P2 可选 |
| npm 发布 `dview` | **不发布**；README 声明 |
| 测试深度 | **shell 冒烟必须**；`lib/accounts`/`store` 单元测试鼓励但不堵发布 |
| Docker 实机 | 合入前至少在一台有 Docker 的机器跑 R5（502）；无则 PR 标明「compose 未在 CI 验证」 |

### 6.3 技术歧义（实现层，易隐性返工）

- **分散 `html_dir` / `image_dir` 与 sidecar「统一 `/data`」**：若有人生产仍用分散绝对路径，compose 挂载会错。SPEC/README 应写 **启用 sidecar ⇒ 必须统一 data_root**。  
- **`proxy_to_render: true` 但运维忘起容器**：502 是对的；启动日志应 **显式警告**（设计已提，确认实现有日志）。  
- **包名 `dview` vs 产品 vibeview**：`package.json` `"name": "dview"` 若误 `npm publish` 有占用风险——与 P2-7 决定绑定。

## 7. 测试与发布就绪条

### 7.1 「可以开 PR」的最低条（现在未完全满足）

- [ ] **P0-10**：独立临时目录起服，覆盖 SPEC §7.1 至少：上传 HTML、错误类型、配额 429、跨账户删除 403、停用 401、`/api/me` 隔离、管理 API 未登录 401 JSON、CLI upload 出 URL。  
- [ ] **`npm test`（或 `npm run smoke`）绿**；与 `smoke:render` 可分开。  
- [ ] README / `config.example.yaml` / SPEC 状态字段一致（P1-1 = 已实现；§8 序更新）。  
- [ ] 安全边界段落与 design §1.2/§8.3 同口径。  
- [ ] 无密钥进仓（`config.yaml` 仍 gitignore）；diff 自审无 token。

### 7.2 「宣称生产可用 sidecar」额外条

- [ ] Docker 实机：compose up → host 上传 → 经 host `/v` 200 → stop render → **502** → 直出模式回滚文档可操作。  
- [ ] 确认 ports 仅为 `127.0.0.1:3001`；data `:ro`；无 config 进容器。  
- [ ] 图/视频 `/raw` 经同一入口可加载（防反代漏路径）。

### 7.3 尚不要求（不要当成发布阻塞）

- 全量单元测试覆盖率、TypeScript、S3、CI 矩阵、npm registry 上架、sandbox 默认开启。

## 8. 最终建议：现在开 PR，还是先做完 X？

### 裁决

**先做完 X = P0-10 冒烟 + SPEC 定稿（最小开放问题）+ 按 §5 拆好提交，然后再开 PR。**  
**不要**在无全链路冒烟的情况下把当前整包未提交改动直接 push 成单一巨型 PR。  
**不要**为了「更安全」再塞 P1-2/P1-5 进同一发布列车。

### 具体动作清单（按序）

1. 用户/维护者确认 §6.1 三项（或接受本文默认：direct、不做 P1-5、拆 PR、不 npm 发布）。  
2. 实现并跑通 **P0-10** `scripts/smoke.sh`。  
3. 更新 SPEC §8/§9 状态（讨论稿 → 本轮定稿；删除过时序）。  
4. 开 PR-A/B/C（或单 PR 多 commit）；PR 描述引用 SPEC ID 与 design 文档。  
5. 有 Docker 时补打 sidecar R5；无则在 PR 标明。  
6. 合入后另开 epic：可选 sandbox（P1-2）、分域（P2-1）、账户 UI（仅当持久化模型已写进 SPEC）。

### 一句话

> **功能面已经超过「讨论稿」该有的完成度；缺口在验证、文档状态与交付切片。先锁门禁再合入，比再堆 P1 更能让这个开源预览服务站稳。**
